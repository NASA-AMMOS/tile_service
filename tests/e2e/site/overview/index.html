Deep Zoom tiles for planetary images

tile_service turns large VICAR and PDS mission images into Deep Zoom (DZI) tile pyramids, so a browser viewer such as OpenSeadragon can pan and zoom from a whole-image overview down to single pixels. It applies the scientific stretch and gamma handling that raw 12- and 16-bit data needs, renders range and geometry products as translucent overlays, and serves thumbnails and per-image metadata. It is the imagery back end of ASTRIA, part of NASA's AMMOS Instrument Data Subsystem, developed by JPL's Multimission Image Processing Laboratory.

What it does

Tiles very large images

VICAR and PDS3 .VIC/.IMG of any size, plus PNG, JPEG and TIFF up to 2 gigapixels, become a DZI pyramid of PNG or JPEG tiles.

Stretches science data

Histogram percent stretch by default, or extrema, relative or none, with linear-to-sRGB gamma unless the product already has it.

Renders overlays

Geometry products (XYZ, UVW, RNG, ARM, ...) become RGBA overlays with an alpha mask over invalid pixels, ready to lay over the source image.

Caches and serves

Results go to a filesystem or S3 cache keyed by a hash of the input and options, so each image is computed once and then served as static tiles.

Thumbnails and metadata

Every tiling also yields a PNG thumbnail and a metadata.json with the histogram, stretch limits and processing settings.

Finds products

An optional finder API lists Mars 2020 and CADRE products in a local archive tree by sol and returns parsed VICAR labels.

End-to-end data flow

Two paths reach tile_service. The ingest path pre-computes tilings as products arrive, so most views are served from cache. The view path is the ASTRIA web client asking for a DZI, its tiles, a thumbnail or the histogram. Dashed boxes are deployment or internal components described generically; only tile_service and astria_ui are in this open source release.

Ingest path

  1. New products land on a shared ingest volume. A file watcher publishes create, modify and move events to an NSQ channel.
  2. A tiler trigger consumes each event and calls GET /image_tiler?image=<path relative to the input root>&force=true. tile_service computes the DZI into its cache; the trigger only logs failures and never reads the body.
  3. A metadata ingester waits for /image_tiler/image_descriptions.xml to answer (its health check), then calls /image_tiler/finder/edr?image=<path> for each file. It merges the returned metadata (instrument, product type, sol, eye, ...) with the VICAR label it parses itself and writes the document to ElasticSearch.

Typical on-premises deployments run two tile_service containers over the same read-only input root and filesystem cache: one serves the web client, one takes ingest traffic. DZI URL overrides make the tile URLs inside each DZI point at the public reverse-proxy path.

View path

  1. The astria_ui Express server delivers the web app and proxies search to ElasticSearch. It does not proxy tile_service in production: the browser talks to tile_service directly or through the deployment's reverse or authentication proxy, at the configured tile_service_url.
  2. To show a product the client builds ?image=<url>&format=png&proxy=<proxy>, adding rdr=, stretch and overlayPreference= parameters when the user changes them, and hands it to OpenSeadragon as a DZI tile source.
  3. OpenSeadragon reads the DZI XML and fetches tiles from the base URL in its Url attribute, retrying 202 and 404 with backoff while a tiling is still being computed.
  4. Thumbnails use &thumb=true; the stretch and histogram panel uses &metadata=true; product type descriptions come from image_descriptions.xml.

Cloud variant

With inputs and cache on S3, an S3 upload notification (wrapped in SQS) invokes TileLambda, which pre-tiles the product into the cache bucket with default settings and deletes the cached tiling when the product is removed. Inputs too large for a Lambda are forwarded over SQS to the REST service. The REST service and the Lambda share the cache bucket and the same configuration, so a default request for a pre-tiled product is answered from cache. Tiles can then be served by redirect to a presigned S3 URL or a data proxy instead of streaming through the servlet.

Request lifecycle

Every request goes through TileService.handleRequest:

  1. Concurrency gateIf tiler_max_concurrent_requests is reached the request gets 503.
  2. Route by pathA tile path /<hash>[/cfg/<hash>]/<proxy>_proxy_image_files/<level>/<col>_<row>.<fmt> goes to the tile server (the hash must be 40 hex characters, otherwise 400). /finder/* goes to the finder. /version, /image_descriptions.xml, /image_config.xml and /openseadragon.min.js are static. The root path with image= is an image request; anything else is 400.
  3. Parse parameters (DziParams)Normalises the image URL (file:// is the same as a relative path; .VIC shares a cache entry with .IMG), infers product and RDR type from the mission filename (or rdr=), decides whether it is an overlay, and whether the options are the defaults. Nominal requests are cached under <sha1 of input>/, custom ones under <hash>/cfg/<sha1 of options>/.
  4. Validate the sourceIs the scheme enabled (enable_s3, enable_http, fs_input_dir)? Then DziTask.filterUrl applies the security filters, which force and filter=false cannot disable: no .., no absolute local paths, http(s) only to public addresses and only when it matches rdr_url_whitelist_patterns. With filtering on, the mission filters (ignored subdirectories, extensions, quicklook and browse products) apply too.
  5. Auxiliary requestsviewer=true returns the HTML viewer at once. thumb, metadata, progress and error never start work: they answer from a running task or the cache, or return 202 / 404.
  6. Cache lookupIf a running task owns the hash, serve from it. Otherwise check the cache (cache_type=fs under fs_cache_loc, or s3 in the cache bucket). A tiling is complete when metadata.json exists; etag.txt detects a changed source, and a stale progress.txt is treated as a zombie. force=true recomputes.
  7. ProcessA miss queues a background DziTask (bounded by max_concurrent_tasks, with an interlock so two servers do not tile the same image). The request waits up to max_wait_time / maxWaitSec, then returns the DZI or 202.
  8. Rewrite and respondThe DZI Url is set for the chosen proxy: this server over http or https, an S3 or data proxy, tile_url, or the dzi_*_override settings. Errors map to status codes: bad input 400, missing file 404, S3 errors their own code, timeouts 202, anything else 500.

Inside a DziTask

  1. Open the sourceLocal file, http range reads or S3, through an LRU page cache in memory and on disk, so large products are read in windows rather than loaded whole.
  2. Read the pixelsRenderedImageReader opens VICAR and PDS through vicario and JAI (plain images through ImageIO, large ones in tile windows). Overlay products go through the image-product library's RDR content classes instead, which produce RGB plus a validity mask.
  3. Stretch and maskHistogram and extrema, then the stretch to 8 bits, then the alpha mask for overlays and CRISP warped-* images (masked 0, unmasked 0.86 for overlays and 1 otherwise), then gamma conversion per gamma_mode with matching PNG gAMA/sRGB chunks.
  4. Build the pyramidThe bundled pyramidio fork cuts a quadtree of tiles using dzi_parallelism threads, and an archiver writes them to the filesystem, S3 or memory (mem_cache_tiles, so tiles can be served while the task runs).
  5. FinishWrites thumbnail.png, params.json and finally metadata.json, which marks the tiling complete. A failure writes error.txt.

CLI and Lambda

The same tiling code runs in three entry points. The CLI and the Lambda use image_tiler.jar; the REST service uses image_tiler.war. All three read the same defaults: servlet init parameters for the REST service, the upper-case environment variables of the same names for the CLI, the Lambda and Docker.

TileCLI

Tile a local product into a filesystem cache

java -Xmx4g -jar image_tiler.jar -i data/NLG_…J01.IMG -m M20 -fc -cl cache

Custom stretch and JPEG tiles, recomputing if cached

java -jar image_tiler.jar -i data/ZLF_…J01.IMG -fc -cl cache \
  -st extrema -sl 1000 -sh 3000 -tf jpg -f

Where would this input be cached?

java -jar image_tiler.jar -i data/NLG_…J01.IMG -pc

Every option

java -jar image_tiler.jar -h

TileLambda

jpl.mipl.mars.tile_service.TileLambda handles SQS-wrapped S3 notifications. On ObjectCreated it applies the URL filter, then tiles the object into the S3 cache, or forwards it to the REST service queue when it exceeds the Lambda's size budget. On ObjectRemoved it deletes the cached tiling. Only default processing is done in the Lambda; custom requests go to the REST service.

Servlet

jpl.mipl.mars.tile_service.TileService is mapped to /* under the image_tiler context on Tomcat. It is stateless apart from the cache, so several servers can share one cache behind a load balancer.

Security model

tile_service has no user authentication of its own; production deployments put it behind an authentication proxy. Its job is to make sure a request can only make it read what the deployment intends.

Local paths stay under the root

Image paths must be relative to fs_input_dir: .., absolute paths and invalid paths are rejected with 400. Finder paths are resolved and normalised, and refused if they leave the root.

No server-side request forgery

http(s) inputs must match the whitelist and resolve only to public addresses: loopback, private, link-local, metadata-service and IPv6-embedded IPv4 forms are refused. Each redirect hop is checked again, with a hop limit and timeouts.

Filters cannot be bypassed

force=true and filter=false relax only the mission filters, never the security filters or the whitelist.

Strict S3 detection

S3 URLs are recognised by exact host labels in linear time; a lookalike such as a query string containing .s3.amazonaws.com is treated as plain https.

Validated cache paths

Tile requests must carry a 40-hex cache hash, so a tile URL cannot name an arbitrary file.

Safe output

Request values are sanitised before they are logged, so a newline cannot forge a log line, and the viewer page percent-encodes request values before placing them in HTML and script.

Finder path normalisation, log sanitising and viewer encoding come with the path-traversal and log-forging fix that follows 6.6.0; the other protections are in 6.6.0. Each of these is exercised by the @security tests in the test procedures. Please report vulnerabilities privately rather than in public issues.

How it is tested

A Playwright feature suite drives the real build: the CLI as a child process and the servlet in Tomcat over HTTP. It checks content rather than exit codes: DZI geometry, tile and thumbnail pixels, metadata fields, and status codes for every rejection. Inputs are public Mars 2020 products from the PDS Imaging Node, pinned by SHA-256, and synthetic VICAR images whose expected pixels are computed from a formula. Nothing needs internal services or credentials; the build uses the public image-product-core library.

The full suite runs on every merge to main and nightly. Every capability, test and result is in the report.
